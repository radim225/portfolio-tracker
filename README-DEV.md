# Developer notes — Investment Tracker

Technical reference produced during the API-research phase. Kept in sync with [lib/t212/](./lib/t212/) and [lib/db/schema.ts](./lib/db/schema.ts).

## Trading 212 API summary

### Base URLs
- Live:  `https://live.trading212.com/api/v0`
- Demo:  `https://demo.trading212.com/api/v0`

Selected via the `T212_ENV` env var (`live` default, `demo` optional).

### Authentication
The public docs list two schemes:

1. **`authWithSecretKey`** — HTTP Basic: `Authorization: Basic base64(API_KEY:API_SECRET)`. Requires both credentials.
2. **`legacyApiKeyHeader`** — Single key: `Authorization: <API_KEY>`. No `Bearer`/`Basic` prefix, raw key.

**This project uses the legacy scheme**, because users generating a key from the T212 app receive a single key. Env var: `T212_API_KEY`.

### Endpoints used

| Purpose | Method | Path | Rate limit |
|---|---|---|---|
| Account totals + cash | GET | `/equity/account/summary` | 1 / 5s |
| Open positions | GET | `/equity/positions` | 1 / 1s |
| Order history | GET | `/equity/history/orders` | 6 / 1m |
| Dividend history | GET | `/equity/history/dividends` | 6 / 1m |
| Transaction history | GET | `/equity/history/transactions` | 6 / 1m |
| Instrument metadata | GET | `/equity/metadata/instruments` | 1 / 50s |
| Exchange metadata | GET | `/equity/metadata/exchanges` | 1 / 30s |

### Pagination
Cursor-based, newest-first. Response shape:

```json
{ "items": [ ... ], "nextPagePath": "/api/v0/.../orders?limit=50&cursor=17..." }
```

- `limit` default 20, max 50.
- Use the entire `nextPagePath` string verbatim as the path for the next request.
- `nextPagePath: null` marks the end of the dataset.

Tail-fetch strategy: daily sync reads newest page only and stops once it sees an `id` already stored in Postgres — keeps normal days inside rate limits even when the account has years of history.

### Rate-limit response headers
- `x-ratelimit-limit`, `x-ratelimit-period`, `x-ratelimit-remaining`, `x-ratelimit-reset`, `x-ratelimit-used`.

Our client ([lib/t212/client.ts](./lib/t212/client.ts)) reads `x-ratelimit-reset` on 429 and sleeps until it, plus a small jitter.

### Currency
Single-currency per account. API docs: _"account, position and result values in the responses will be in the primary account currency."_ For this project's account that's **CZK** — no in-app FX conversion is performed on monetary fields. Native instrument currency appears on instrument metadata only and is shown for reference in the positions table.

## Database (Neon / Postgres)

Schema lives in [lib/db/schema.ts](./lib/db/schema.ts). Migrations are generated by `drizzle-kit generate` into [lib/db/migrations/](./lib/db/migrations/) and applied via `pnpm db:migrate`.

Two drivers are used:
- **`drizzle-orm/neon-http`** — request path (Next.js server components on Vercel). HTTP fetch-based; no connection pool warmup.
- **`drizzle-orm/neon-serverless`** — long-running scripts (`pnpm sync`, `pnpm backfill`). WebSocket `Pool` reuses a single connection across many queries.

Cold starts on Neon free tier: first request after ~5 min idle can take 2–3 s. Mitigated by:
- `loading.tsx` skeletons on every page.
- Shared queries via React `cache()` so one wake-up serves all tabs on a navigation.

## Daily sync

Cron config in [.github/workflows/daily-sync.yml](./.github/workflows/daily-sync.yml) — two entries to cover DST:

```yaml
- cron: '55 22 * * *'   # CET  (winter, UTC+1) → 23:55 Prague
- cron: '55 21 * * *'   # CEST (summer, UTC+2) → 23:55 Prague
```

Idempotency: all inserts are upserts on primary keys (`id`, `reference`, `date`) so a duplicate fire across DST changeover is a no-op.

## MCP server

Local stdio server in [mcp/server.ts](./mcp/server.ts). Exposes read-only tools; no `raw_query`, no order placement.

Tools: `portfolio_overview`, `list_positions`, `closed_trades`, `dividends`, `cashflow`, `portfolio_timeline`, `sync_status`.

Claude Code config:

```json
{
  "mcpServers": {
    "trading212": {
      "command": "tsx",
      "args": ["/absolute/path/to/Investment_tracker/mcp/server.ts"],
      "env": {
        "DATABASE_URL": "postgresql://..."
      }
    }
  }
}
```

Production users can compile with `tsc` and run the JS directly.

## FIFO implementation

Buy → sell pairing in [lib/calc/fifo.ts](./lib/calc/fifo.ts). Per-ticker queue of open buy lots (FIFO); sells consume oldest lots first; a single sell spilling across multiple lots produces multiple `ClosedTrade` rows with correct per-lot cost basis.

Test scenarios in [lib/calc/fifo.test.ts](./lib/calc/fifo.test.ts):

1. Simple 1:1 buy → sell.
2. Partial sell (lot remains open).
3. Multiple buys, then one sell within the oldest lot.
4. Cross-lot sell spilling into the next lot.
